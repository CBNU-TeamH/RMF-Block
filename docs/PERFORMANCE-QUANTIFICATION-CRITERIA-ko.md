- 도구를 측정 대상에 맞춰 선택했다 (vite-bundle-visualizer=번들 구성, Network 탭=로딩 시간,
  Lighthouse=종합 점수) — 하나의 도구로 모든 걸 재려 하지 않았다.
- 측정 조건을 고정했다 (Slow 3G, 캐시 없음, 고정 Wi-Fi) — 조건이 바뀌면 숫자가 의미 없어진다.
- 10회 반복 측정 후 평균을 냈다 — 단발성 숫자는 노이즈에 취약하다.
- Before/After 숫자를 표로 명시했다 ("느려졌다/빨라졌다"가 아니라 "57.25s → 30.62s, 47%").

이 프로젝트는 페이지 로딩이 아니라 **LAN 내 실시간 동기화 지연**이 핵심이라 Slow 3G·번들 사이즈
같은 조건은 그대로 옮길 수 없다. 대신 "도구를 대상에 맞추기 / 조건 고정 / 반복 평균 / before-after
표"라는 방법론 자체를 아래 6개 항목에 적용한다.

## 측정 클래스 — 방법을 결정하는 것은 "인과가 몇 대의 머신에 걸쳐 있는가"

항목별로 도구를 하나씩 고르기 전에, 먼저 **원인과 결과를 누가 관측하는가**를 본다. 이게 갈리면
필요한 대책이 통째로 달라지기 때문이다. `docs/SRS-ko.md` §3.4.1의 6개 항목은 세 클래스로 나뉜다.

| 클래스 | 항목 | 원인과 결과의 관측 지점 | 필요한 대책 |
|---|---|---|---|
| **A. 동일 클라이언트 내 인과** | NFR-PER-003 | 같은 탭 — 시계가 하나뿐 | 없음. 그 페이지에서 단독 측정 |
| **B. 클라이언트 간 인과** | NFR-PER-002, NFR-PER-004, NFR-PER-005 | 서로 다른 머신 — 시계가 둘 | NTP 동기화 + 양방향 측정 (통제 불가 기기는 전송 경로별 단일 클록 대안 — 아래) |
| **C. 시간 측정이 아님** | NFR-PER-001 / 006 | 시각이 아니라 상태·양 | 클록 무관 |

### 클래스 A — NFR-PER-003 (참가 후 3초 이내 문서 트리 + 접속자 목록 표시)

원인(참가 액션)과 결과(두 UI 렌더 완료)가 **같은 브라우저 탭**에서 일어난다. 관측자가 하나이므로
클록 스큐 문제가 애초에 생기지 않는다 — 클래스 B가 쓰는 NTP 동기화도, ack 왕복도 필요 없다.

- **도구**: 해당 페이지의 `performance.now()`. Playwright로 자동화하면 `click` → `waitForSelector`
  시간차로도 같은 값을 얻는다.
- **`Date.now()`가 아니라 `performance.now()`** — 후자는 monotonic이라 측정 도중 NTP 보정이 시계를
  건드려도 값이 튀지 않는다. 단일 클록 측정이라도 이건 지킨다.
- 6개 중 유일하게 velog 글의 "초기 로딩" 측정과 직접 대응하는 항목 — 네트워크 조건 고정 방법론을 그대로
  적용한다. 반복 횟수와 판정 통계는 아래 "공통 측정 원칙"을 따른다(20회 이상, p95).

### 클래스 B — 클라이언트 간 전파 (각 1초 이내)

| 항목 | 원인 → 결과 |
|---|---|
| NFR-PER-002 | A가 블록 수정 → B 화면에 반영 |
| NFR-PER-004 | A가 채팅 전송 → B에게 전달 |
| NFR-PER-005 | 발표자가 화면 위치/스크롤 변경 → 참여자 화면에 반영 |

셋 다 원인과 결과가 **다른 머신**에서 일어난다. 두 브라우저가 각자 `Date.now()`를 찍어 빼면 실제
지연이 아니라 시계 오프셋을 재게 된다. 그리고 이 오차는 랜덤 노이즈가 아니라 **상수 편향**이라
반복 평균으로 지워지지 않는다 — 300ms 틀어진 시계로 100번 재면 100번 다 300ms 틀린다.

#### 기본 방식: NTP 동기화 + 메시지 타임스탬프 + 양방향 측정

1. 측정 직전 두 클라이언트와 서버를 **동일 LAN의 같은 NTP 서버**에 동기화하고, `chronyc tracking`으로
   수렴을 확인한 **뒤에** 측정 페이지를 (재)로드한다 — 아래 `timeOrigin`은 페이지 로드 시점에 고정되므로,
   페이지를 먼저 열어두고 나중에 동기화하면 그 보정이 반영되지 않는다.
2. 송신 측이 전송 시각 `t0`을 기록한다. `t0`을 상대에게 전달하는 방법은 전송 경로마다 다르다:
   - **채팅(NFR-PER-004)**: App WS 메시지 페이로드에 `t0`을 싣는다.
   - **블록 편집(NFR-PER-002)**: 매 회차 고유한 **마커 문자열**을 입력하고, 송신 측은 `마커 → t0`, 수신 측은
     `마커 → t1`을 각자 로그로 남겨 사후에 마커로 조인한다. Yorkie op에 측정용 필드를 추가하지 않아도 된다.
   - **발표자 위치(NFR-PER-005)**: 스크롤 값 자체를 마커로 쓴다 — 회차마다 서로 다른 목표 위치로 이동시키고
     `위치 → t0` / `위치 → t1`을 조인한다.
3. 수신 측이 화면 반영 완료 시점에 `t1`을 찍고 `t1 - t0`을 기록한다.
4. **A→B와 B→A를 양쪽 다 잰다.**

4번은 판정용이 아니라 진단용이다. **합격/불합격은 항상 방향별로 따로 판정한다** — 두 방향의 평균으로
판정하지 않는다. A→B가 1400ms, B→A가 600ms면 평균은 1000ms로 "통과"처럼 보이지만, A→B를 겪는 사용자는
전원 예산을 어긴 상태다.

평균/차이로 δ를 구하는 관계식 자체는 **두 방향의 실제 편도 지연이 같다는 대칭 가정 위에서만** 성립한다
— 잔여 오프셋 δ가 있으면 한 방향은 `(참값 + δ)`, 반대 방향은 `(참값 − δ)`로 읽히므로 평균이 δ를 상쇄하고
차이가 `2δ`를 준다는 것인데, 이 프로젝트에서는 그 대칭이 실제로 깨진다 — 클라이언트 렌더 처리 시간이
기기마다 다르다(폰 vs 노트북). 즉 이 차이값만으로는 시계 스큐와 경로·렌더 비대칭을 구분할 수 없다.
그래서 오프셋 숫자는 `chronyc tracking`이 주는 실측값을 쓰고, A→B/B→A 차이는 "시계가 안 맞거나 경로가
비대칭"이라는 **점검 신호**로만 쓴다.

**어떤 시계를 읽나**: 클래스 A와 달리 여기선 머신 간 비교가 필요해 `performance.now()`를 그대로 쓸 수
없다(페이지마다 원점이 다르다). 벽시계에 고정되면서도 단조 증가하는
`performance.timeOrigin + performance.now()`를 쓴다 — 맨 `Date.now()`는 측정 도중 NTP 보정이 시계를
점프시키면 값이 튄다. 반대로 `timeOrigin`은 페이지 로드 시점의 벽시계로 고정되므로, 기본 방식 1단계대로
동기화를 끝낸 **뒤에** 페이지를 연다.

**예산 대비로 충분한가**: 동일 LAN·동일 NTP 서버 기준 오프셋은 보통 1~10ms고 예산은 1000ms다(≈1%).
게다가 이 방식은 요구사항 문구("다른 사용자 **화면에** 1초 이내 반영")가 실제로 묻는 **편도 값을
직접** 준다 — 왕복을 재서 보정할 필요가 없다.

**동기화 품질을 측정 조건에 기록한다**: `chronyc tracking`(또는 `ntpq -p`)이 추정 오프셋과 dispersion을
숫자로 주므로 "동기화 오차 ±Xms"를 그 회차 측정 조건의 일부로 남긴다. 위 양방향 차이값이 이 오프셋보다
훨씬 크면 점검 신호가 울린 것 — 시계든 경로든 뭔가 비대칭이라는 뜻이다.

**PTP는 쓰지 않는다**: 마이크로초급 정확도는 NIC 하드웨어 타임스탬핑과 스위치의 boundary/transparent
clock 지원이 있어야 나오고, 소프트웨어만으로는 수십~수백 µs에 설정 비용도 든다. 1000ms 예산에는 과하다.

#### 대안: 시계를 통제할 수 없는 클라이언트 — 전송 경로가 방법을 정한다

`docs/SRS-ko.md` §2.4는 **모바일 웹 브라우저를 지원 범위에 넣는다.** 폰에서는 `chronyd`를 띄울 수도,
오프셋을 읽을 수도 없다 — 내가 관리하지 않는 팀원 기기도 마찬가지다. 이때는 상대 시계를 아예 읽지
않는 방식으로 바꾼다. 다만 **어느 시계 하나로 잴 수 있는지는 그 항목의 데이터가 어느 경로로 가는지가
정한다**:

| 경로 | 항목 | 우리 코드가 relay 지점에 있는가 | 대안 |
|---|---|---|---|
| App WS (Next.js 커스텀 서버) | NFR-PER-004 채팅 | 예 — 서버가 수신자마다 `send()` | 서버 단일 클록 + 렌더 ack |
| Yorkie 직결 (클라이언트 ↔ Yorkie) | NFR-PER-002 블록 편집, NFR-PER-005 발표자 위치 | 아니오 — 클라이언트가 `yorkie.Client`로 Yorkie에 직접 붙고(`app/(workspace)/presence-provider.tsx`), App 서버는 이 트래픽을 보지 않는다. Yorkie는 Go 서버라 계측 훅을 넣을 수도 없다 | 송신 측 단일 클록 왕복 에코 |

##### App WS 경로 (NFR-PER-004): 서버 단일 클록 + 렌더 ack

1. 서버가 relay할 때 자기 클록으로 `T0`을 찍는다 — **그 수신자에게 `send()` 하기 직전에.** 8명에게
   루프로 broadcast하면 마지막 수신자는 첫 수신자보다 늦게 나가므로 수신자별로 따로 찍어야 한다.
2. 수신 클라이언트가 화면 반영 후 가벼운 ack를 되쏜다(아래 rAF 주의).
3. 서버가 ack 도착 시각 `T1`을 **역시 자기 클록으로** 찍는다.

두 시각이 서버 프로세스의 한 시계에서만 나오므로 스큐가 소멸한다. 단, `T1 - T0`은 **하행 + 렌더 +
상행**이라 사용자가 겪지 않는 상행 홉이 섞여 있고 A의 입력~서버 구간은 빠져 있다. 서버가 A의 op를
받은 시각 `T_in`도 함께 찍어 `T1 - T_in`을 쓰면 누락 구간이 "A의 로컬 입력 처리 + A→서버 네트워크"로
줄어든다.

구현 시: 전송마다 correlation id를 실어 서버가 `id → T0` 맵으로 ack를 매칭한다. 서버 쪽 시각도
`Date.now()`가 아니라 `process.hrtime.bigint()`를 쓴다 — 단일 머신이라도 NTP 보정이 벽시계를 점프시킬
수 있다. 이 ack 계측은 **측정 모드에서만 켜지는 훅**이고 프로덕션 빌드에 남으면 안 된다.

##### Yorkie 직결 경로 (NFR-PER-002/005): 송신 측 단일 클록 왕복 에코

relay 지점이 없으니 시계를 **송신 클라이언트 A** 쪽 하나로 모은다.

1. A가 편집(또는 스크롤)하는 순간 `performance.now()`로 `t0`을 찍는다. 마커는 기본 방식 2단계와 같다.
2. B가 그 변경을 화면에 반영하면(이중 rAF, 아래) 측정 모드 전용 presence 필드에 그 마커를 실어 에코한다.
3. A가 `doc.subscribe("others")`로 에코를 받는 순간 `t2`를 찍는다.

`t2 - t0` = A→B 편도 + B 렌더 + B→A 편도다. 판정은 **보수적으로만** 한다:

- `t2 - t0 ≤ 1000ms`면 그 안에 든 편도(A→B + 렌더)도 당연히 1000ms 이하 — **합격**.
- `t2 - t0 > 1000ms`면 편도가 예산 안인지 밖인지 이 값만으로는 알 수 없다 — **판정 불가**. 시계를
  통제할 수 있는 기기로 기본 방식(NTP)을 다시 돌려 판정한다.

에코 역시 ack와 같은 **측정 모드 전용 훅**이고 프로덕션 빌드에 남으면 안 된다.

#### "화면 반영 완료" 시점을 잡는 법 (모든 방식 공통)

`requestAnimationFrame` 콜백은 그 프레임이 **페인트되기 직전**에 실행된다. 그 안에서 시각을 찍으면
페인트 전을 재는 것이다. 페인트 이후를 잡으려면 **이중 rAF**를 쓴다:

```js
requestAnimationFrame(() => requestAnimationFrame(() => markRendered(id)));
```

두 번째 콜백은 다음 프레임의 시작이고, 그 시점엔 이전 프레임이 이미 화면에 나가 있다.

rAF는 **백그라운드 탭에서 멈춘다.** 측정 중인 탭은 항상 foreground여야 하고, 클라이언트마다 별도 창을
쓴다 — 한 창에 여러 클라이언트를 탭으로 띄우면 뒤에 깔린 탭은 rAF가 돌지 않아 `t1`이 찍히지 않거나
탭이 다시 앞에 나올 때까지 밀려 찍힌다.

#### 렌더 시간만 분리하고 싶을 때 — 진단용이지 판정용이 아니다

아무 작업 없이 즉시 에코만 하는 ping/pong을 같은 방식으로 재 `T_network`를 얻고 빼면 클라이언트 렌더
처리 시간이 근사된다. 두 가지를 지킨다:

- **합격/불합격 판정은 뺄셈하지 않은 값으로 한다.** 뺄셈은 "시간이 어디서 갔나"를 보는 진단이다.
- ping 페이로드가 실제 블록 op보다 훨씬 작으면 두 홉 비용이 같다는 가정이 약해진다 — 크기를 맞추거나
  근사임을 명시한다.

### 클래스 C — NFR-PER-001 / 006

시각을 재는 항목이 아니라서 클록 논의가 적용되지 않는다.

| 항목 | 재는 것 | 도구/방법 |
|---|---|---|
| NFR-PER-001 (8인 이하 정상 동작) | 8명 동시 접속 시 에러율·연결 끊김·CRDT 수렴 실패 여부 | Node 스크립트로 Yorkie 클라이언트 SDK 8개 동시 구동, 또는 Playwright 헤드리스 세션 8개 |
| NFR-PER-006 (클라이언트 메모리 500MB 이하) | 정의된 "일반적인 협업 시나리오"(제안: 10분 세션, 블록 편집 20회·채팅 10건, 파일 블록 제외) 중 피크 메모리 | Chrome 작업 관리자 "Memory footprint" 주기 샘플링 (heap snapshot은 누수 진단용) |

NFR-PER-001은 독립 항목이라기보다 **나머지 다섯 개를 감싸는 조건**으로 취급한다 — "8명 부하 하에서도
002/003/004/005가 여전히 기준을 만족하는가"가 실제로 묻는 것이다. NFR-PER-006은 "일반적인 협업
환경"이 무엇인지부터 시나리오로 못박아야 측정이 재현 가능해진다.

**NFR-PER-001 판정 기준 (제안 — 팀 미합의, 잠정값)**:

- **실패 조건**: 셋 중 하나만 걸려도 그 회차는 실패로 판정한다.
  - 세션 중 연결이 끊기는 클라이언트가 1개라도 발생. 연결은 **두 개**다 — App WS(채팅)와 Yorkie 스트림.
    Yorkie SDK는 WebSocket이 아니라 HTTP 기반 Connect/gRPC-web 스트림을 쓰므로 WS 끊김만 보면 문서 동기화
    쪽 끊김을 놓친다. Yorkie 쪽은 `doc.subscribe("connection", …)` 이벤트의
    `StreamConnectionStatus.Disconnected`로 관측한다.
  - 활동 종료 후 CRDT 상태가 모든 클라이언트에서 동일 내용으로 수렴하지 않음.
  - 시나리오상 **예상하지 않은** 에러 응답(HTTP 4xx·5xx 또는 WS 에러 프레임)이 1건 이상 발생. 정상 동작인
    4xx(세션 만료 401, 업로드 한도 초과 413 등)는 세지 않는다 — 이 워크로드에서 그런 응답이 나올 경로가
    있다면 회차 시작 전에 목록으로 적어둔다.
- **세션 길이**: 8명 동시 접속 상태로 **10분** 고정.
- **사용자당 워크로드**: 10분 동안 블록 편집 **20회**, 채팅 전송 **10회**를 버스트 없이 고르게 분산.
- **반복**: 20회 이상, **20회 중 실패 0건이어야 통과**. 이 항목은 발생 여부 판정이라 p95를 적용하지
  않는다. 0/20이 보장하는 범위도 기록해둔다 — rule of three에 따라 n회 중 0건이면 95% 신뢰로 실패율이
  `3/n` 미만, 즉 0/20은 "실패율 15% 미만"까지만 말해준다. 더 강한 주장이 필요하면 n을 늘린다.
- **비용**: 10분 × 20회 = 최소 200분, 기기(또는 헤드리스 세션) 8개. 회차 사이 초기화 시간은 별도다.

**NFR-PER-006 판정 기준 (제안 — 팀 미합의, 잠정값)**: "일반적인 협업 시나리오"를 NFR-PER-001과 같은
워크로드(세션 10분, 블록 편집 20회, 채팅 10건)로 고정하고 **파일 블록은 제외**한다 — 파일 업로드/뷰어의
메모리는 이 시나리오가 다루는 문제가 아니라서다. 측정값은 세션 전체의 **피크 메모리**이고,
`docs/SRS-ko.md`의 500MB 임계값과 직접 비교한다.

- **무엇을 읽나**: Chrome 작업 관리자의 해당 탭 **"Memory footprint"**. 이것은 DOM 노드를 포함한 OS
  메모리고, 옆의 "JavaScript memory"는 JS 힙만이다. SRS의 "클라이언트 메모리 사용량"에 가까운 건 전자다.
- **피크를 잡는 법**: 세션 내내 일정 간격(예: 10초)으로 샘플링해 최댓값을 쓴다.
- **heap snapshot은 판정에 쓰지 않는다.** JS 힙만 세고, 스냅샷을 찍기 전에 GC를 강제하므로 찍힌 값이
  피크보다 작게 나온다. 값이 기준에 근접하거나 세션 동안 계속 오르면 그때 누수 진단용으로 쓴다.
- **`performance.measureUserAgentSpecificMemory()`는 쓸 수 없다** — secure context(HTTPS)와 cross-origin
  isolation(COOP/COEP)이 필요하고 아직 실험 기능이다. 이 앱은 LAN에서 HTTP로 돈다.
- **측정 브라우저**: 데스크톱 Chrome으로 고정한다(잠정). 모바일은 탭 단위 OS 메모리를 읽을 도구가 마땅치
  않아 판정을 보류하고, 필요해지면 방법부터 따로 정한다.

## 공통 측정 원칙

velog 글의 방법론에서 계승한 것 + 위 논의에서 추가된 리그 조건:

1. **측정 조건을 문서에 고정한다** — 참가자 수, 네트워크(LAN Wi-Fi 대역 vs 유선), 브라우저, 호스트
   하드웨어 기준선, 그리고 클래스 B를 쟀다면 **그 회차의 NTP 동기화 오차**. 조건이 매번 다르면 숫자를
   비교할 수 없다.
2. **테스트 리그는 물리적으로 분리된 기기 2대 이상을 실제 LAN 위에서 쓴다** — 네트워크 네임스페이스로
   분리한 프로세스도 대안. 클라이언트를 전부 한 머신에 몰아두면 네트워크 비용이 0에 수렴해 숫자가
   무의미해진다. **클래스 A도 예외가 아니다** — 서버가 localhost면 3초 기준을 검증한 게 아니다.
   (클록 스큐 대책과는 별개 문제다. ack 방식을 쓰든 안 쓰든 이 조건은 따로 필요하다.)
3. **판정 통계는 p95로 통일한다** — 평균은 꼬리 지연을 가리고, 중앙값은 절반의 사용자만 보장한다.
   **매 항목 20회 이상 반복 측정**하고 p95를 예산과 비교해 합격/불합격을 정한다(5~10회로는 p95 자체가
   무의미하다). 평균/중앙값은 참고용으로 함께 기록해도 되지만 판정에는 쓰지 않는다. 단일 실행값은
   기준으로 인정하지 않는다.
4. **측정 도구는 재는 대상에 맞춰 고른다** — 클래스가 이미 이걸 결정한다. Lighthouse류는 페이지 로드
   프로파일러라 클래스 B(정상 작동 중 동기화 지연)에는 맞지 않는다.
5. **현재 베이스라인(최적화 전 숫자)을 먼저 기록한다** — 지금 통과/실패 여부와 여유/부족분을 먼저
   알아야 `ROADMAP.md` Phase 5에서 무엇을 고칠지 우선순위를 매길 수 있다.

## 경쟁 도구 대비 네트워크 열화 시나리오 검증

> 위 6개 NFR-PER 항목은 **RMF-Block 자체가 SRS 기준을 통과하는지**를 잰다. 이 섹션은 다른 질문에
> 답한다 — **같은 열화된 네트워크에서 RMF-Block이 Notion/Google Docs보다 나은가.** 판정 기준이
> 다르므로(SRS 절대 임계값 vs 도구 간 상대 비교) 위 6개 항목과 같은 표에 섞어 채점하지 않는다.

### 이 비교가 실제로 재는 것

RMF-Block 서버는 호스트의 LAN 안에 있고, Notion/Google Docs는 반드시 인터넷을 거친다. 같은 도서관
와이파이에 붙어 있어도 RMF-Block 트래픽은 "기기 → AP → LAN 서버"만 혼잡 구간을 지나가는 반면
Notion/Google Docs는 "기기 → AP → 도서관 업링크 → 인터넷 → 클라우드"까지 전부 지나간다. 이 실험은
그 구조적 차이가 실제 체감 성능 차이로 이어지는지 검증하는 것이지 우연한 비교가 아니다 — 보고서·
발표에 이 문장을 그대로 명시해야 결과 해석이 정확해진다.

### 조건 재현 방법 두 가지

**A. 실측 후 재현 (in-situ measurement, 권장)** — 시험기간 도서관에서 `ping`/`iperf3`로 실제
RTT·jitter·packet loss·대역폭을 재고, 그 숫자를 아래 도구 파라미터에 그대로 넣는다. "측정 조건을
문서에 고정한다"는 위 공통 측정 원칙 그대로 — 임의의 숫자를 쓰면 재현 불가능하다.

**B. 통제된 네트워크 에뮬레이션** — 노드별로 적용 지점이 다르다:

| 노드 | 도구 |
|---|---|
| 서버(App/WS Server, Linux) | [`tc netem`](https://oneuptime.com/blog/post/2026-03-04-simulate-network-latency-packet-loss-tc-netem-rhel-9/view) — 지연·손실·jitter·순서뒤섞임까지 제어 |
| Windows 클라이언트 | [Clumsy](https://webrtc.ventures/2024/06/how-do-you-simulate-unstable-networks-for-testing-live-event-streaming-applications/) |
| macOS 클라이언트 | [Network Link Conditioner](https://www.avanderlee.com/debugging/network-link-conditioner-utility/) (Apple 무료 제공) |
| 도구 설치 불가 환경(도서관 공용 PC 등) | [Chrome DevTools Custom throttling profile](https://developer.chrome.com/docs/devtools/settings/throttling) — 그 탭 트래픽만 latency/packet loss %/대역폭 개별 설정 |

A로 잰 실측값을 B의 파라미터로 주입하는 조합이 가장 신뢰도 높다.

### 시나리오 프리셋 (제안 — 팀 미합의, 잠정값)

| 시나리오 | RTT 추가 | packet loss | 비고/근거 |
|---|---|---|---|
| 기준선(혼잡 없음) | +0ms | 0% | 새벽 시간대 빈 도서관 또는 유선 |
| 경도 혼잡 | +20~50ms | ~1% | 일반 캠퍼스 WiFi 실측 P90 대역 — [Tsinghua 캠퍼스 대규모 WiFi 지연 연구](https://dl.acm.org/doi/10.1145/2906388.2906393)(47,000+ 기기, P90 ~20ms/P99 ~250ms) |
| 중도 혼잡 — **시험기간 도서관 목표값** | 실측값(A) 우선, 없으면 +100~150ms | 웹 검색상 공용 WiFi 혼잡 실측치로 수 %대 손실률이 언급되나 1차 출처 특정 안 됨 → **A(실측)로 직접 확인 권장** |
| 고도 혼잡(최악) | +300ms 이상 | 10%+ | [Chrome DevTools "Slow 3G" 계열 프리셋](https://www.debugbear.com/blog/chrome-devtools-network-throttling) 기준선에서 loss 추가 |

### 태스크 설계

"애국가 1·2절 교대 입력" 하나만으로는 순차 편집 패턴밖에 못 본다. 아래 5개를 세트로 구성해 각기
다른 협업 패턴을 커버한다 — 전부 세 도구(RMF-Block/Notion/Google Docs) 동일 조건에서 반복 가능한
것만 골랐다. 각 태스크는 세 도구 모두에서 반복하고, 텍스트 길이·구조는 도구 간 고정한다.

| # | 태스크 | 관찰 대상 |
|---|---|---|
| 1 | **순차 교대 입력**(원안 — 애국가 1·2절, A/B가 한 줄씩). 1절은 A 선공/B 후공, 2절은 B 선공/A 후공으로 **순서 카운터밸런싱**해 타자 속도 편차를 상쇄한다(within-subjects counterbalancing) | 기본 전파 지연·체감 완료 시간 |
| 2 | **동시 충돌 편집** — 같은 문단/같은 줄을 A·B가 동시에 수정 | 충돌 해소·병합 동작 — CRDT(RMF-Block) vs Google Docs의 OT vs Notion 자체 알고리즘이 혼잡 네트워크에서 다르게 깨지는지 |
| 3 | **자유 동시 편집** — 턴 강제 없이 각자 원하는 위치에 5분간 자유롭게 타이핑해 문서 하나를 공동 완성 | 순서를 강제하지 않는 실제 사용 패턴에 더 가까운 지연·충돌 빈도 |
| 4 | **파일/이미지 삽입 포함** — 텍스트 입력 중간에 이미지 1~2개 첨부 | 텍스트보다 무거운 payload가 혼잡 네트워크에서 업로드·동기화에 걸리는 시간 |
| 5 | **편집 중 단절→재연결** — 편집 도중 한쪽 클라이언트만 네트워크를 30초 끊었다가 복구 | 재동기화 시간·데이터 유실 여부 — RMF-Block의 30초 grace period(FR-022-12)와 직접 비교 가능한 유일한 태스크. 세 도구 모두 오프라인 편집 후 재연결 시 병합 동작이 달라 회복력 비교에 적합 |

시나리오(위 표)마다 태스크 5개를 전부 돌리는 건 시간상 무리이므로, 태스크 1(원안)은 전 시나리오
반복하고 태스크 2~5는 "중도 혼잡(도서관 목표값)" 시나리오 하나에서 3개 도구만 비교해도 된다 —
어디까지 돌릴지는 팀이 시간 예산에 맞춰 정할 것(제안일 뿐, 팀 미합의).

| 지표 | 방법 | 근거 |
|---|---|---|
| 총 소요시간 | 시작~완료 스톱워치 | 주 판정 지표 |
| 줄 단위 전파 지연 | 클래스 B 방식(이중 rAF, 송신측 `t0`/수신측 `t1`) 재사용 | 진단용 — "왜 차이 나는지" 설명 |

| 파일 업로드 반영 지연 | 첨부 시작~상대 화면에 표시 완료까지(태스크 4, 줄 단위 전파 지연과 동일 방식으로 측정) | RMF-Block 고유 파일 블록 기능(FR-022-13/14) 포함 검증 |
| 재연결·끊김 횟수 / 재동기화 시간 | 세션 중 WS/네트워크 드롭 여부 및 복구까지 걸린 시간 (태스크 5) | NFR-PER-001 판정 기준과 동일 방식, RMF-Block은 FR-022-12(30초 grace period)와 비교 |
| (선택) 체감 사용성 | SUS 설문 또는 NASA-TLX 워크로드 설문 | 협업 에디터 사용자 연구에서 표준적으로 쓰이는 정성 지표 — 참고: [Google Docs가 동시 사용자 10명 초과 시 지연 급증](https://ieeexplore.ieee.org/document/7497258/)한다는 실측 사례 |

판정은 뺄셈 값(줄 단위 지연)이 아니라 최종 소요시간을 주 지표로 쓰고, 줄 단위 지연은 진단용으로만
쓴다 — 클래스 B "뺄셈은 판정용이 아니라 진단용" 원칙과 동일.

### 반복·통계

위 공통 측정 원칙을 그대로 따른다: 조건을 고정하고, 가능한 만큼 반복(현실적으로 20회는 무리이므로
최소 5~10회 목표) 후 p95를 병기하며, "RMF-Block vs Notion vs Google Docs" 표로 제시한다. 단일 실행값은
근거로 인정하지 않는다는 원칙도 동일하게 적용.

## Vitest가 맡는 것 / 맡지 않는 것

레포에는 이미 Vitest + `@testing-library/react`가 있고 `docs/testing.md`가 4개 레이어를 정의한다.
여기서 경계를 명시해둔다.

**벽시계 숫자는 Vitest에서 재지 않는다.** 두 가지 구조적 이유가 있고, 둘 다 설정을 바꿔서 해결할
문제가 아니다:

- DOM 환경이 happy-dom이라 **페인트가 존재하지 않는다** (ADR-004 §3). `render()`가 주는 건 DOM
  트리지 렌더된 프레임이 아니므로, "사용자 화면에 반영된 시점"을 정의할 수가 없다.
- `vitest.config.mts`가 `pool: "forks"`이고 워커 수가 머신 코어에 따라 변한다(설정 주석이 직접
  경고한다). 타이밍 노이즈가 신호를 덮는다.

여기에 ms 단언을 넣으면 `.githooks/pre-push`와 CI에서 흔들리는 테스트가 된다. 대신 Vitest는
**브라우저 하네스가 비싸게 확인할 것들을 결정론적으로** 가져간다 — 셋 다 기존 레이어에 그대로 들어간다:

1. **임계값·집계 로직 → `lib/` 레이어.** 샘플에서 p50/p95를 내고 예산과 비교하는 부분은 순수 로직이다.
   `docs/testing.md`의 기존 규칙 "Every limit gets a test at exactly that value"가 문자 그대로
   적용된다 — 1000ms 예산이면 999 / 1000 / 1001에 테스트를 둔다.
2. **왕복 횟수·구조적 속성 → 클라이언트 컴포넌트 레이어.** 셋 중 값어치가 가장 크다. 예산을 실제로
   깨뜨리는 건 "느린 코드"가 아니라 **왕복이 하나 늘어나는 변경**이기 때문이다. 참가 응답에 접속자
   목록이 이미 실려 오는데 별도 fetch를 한 번 더 하도록 바뀌면, 3초 예산이 2×RTT부터 시작한다.
   `fetch` 스파이로 "두 UI가 참가 응답 하나에서 렌더된다"를 단언하면 타이밍 없이 그 회귀를 잡는다.
   클래스 B도 같은 모양 — WS 프레임에서 바로 렌더하는가, 아니면 refetch를 트리거하는가.
3. **계측 훅의 계약 → `lib/`/`server/` 레이어.** 클래스 B의 ack·에코 계측이 플래그 없이는 꺼져 있는지,
   프로덕션 설정에서 켜지지 않는지. 계측이 조용히 프로덕션에 남아 있는 것 자체가 버그다.

알고리즘 회귀를 막고 싶으면 ms가 아니라 **호출 횟수**를 단언한다(`vi.fn()` 스파이) — 머신 독립적이라
CI 게이트로 쓸 수 있다. `vitest bench`는 머신마다 숫자가 달라 게이트가 될 수 없으므로 도입하지 않는다.
