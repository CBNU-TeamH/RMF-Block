핵심은 특정 최적화 기법(lazy loading, SVG 스프라이트, 폰트 서브셋 등)이 아니라 **측정 방법론**이다:

- 도구를 측정 대상에 맞춰 선택했다 (vite-bundle-visualizer=번들 구성, Network 탭=로딩 시간,
  Lighthouse=종합 점수) — 하나의 도구로 모든 걸 재려 하지 않았다.
- 측정 조건을 고정했다 (Slow 3G, 캐시 없음, 고정 Wi-Fi) — 조건이 바뀌면 숫자가 의미 없어진다.
- 10회 반복 측정 후 평균을 냈다 — 단발성 숫자는 노이즈에 취약하다.
- Before/After 숫자를 표로 명시했다 ("느려졌다/빨라졌다"가 아니라 "57.25s → 30.62s, 47%").

이 프로젝트는 페이지 로딩이 아니라 **LAN 내 실시간 sync latency**가 핵심이라 Slow 3G·번들 사이즈
같은 조건은 그대로 옮길 수 없다. 대신 "도구를 대상에 맞추기 / 조건 고정 / 반복 평균 / before-after
표"라는 방법론 자체를 아래 6개 항목에 적용한다.

## 측정 클래스 — 방법을 결정하는 것은 "인과가 몇 대의 머신에 걸쳐 있는가"

항목별로 도구를 하나씩 고르기 전에, 먼저 **원인과 결과를 누가 관측하는가**를 본다. 이게 갈리면
필요한 대책이 통째로 달라지기 때문이다. `docs/SRS-ko.md` §3.4.1의 6개 항목은 세 클래스로 나뉜다.

| 클래스 | 항목 | 원인과 결과의 관측 지점 | 필요한 대책 |
|---|---|---|---|
| **A. 동일 클라이언트 내 인과** | NFR-PER-003 | 같은 탭 — clock이 하나뿐 | 없음. 그 페이지에서 단독 측정 |
| **B. 클라이언트 간 인과** | NFR-PER-002, NFR-PER-004, NFR-PER-005 | 서로 다른 머신 — clock이 둘 | 하네스가 잰 시계 차이(θ)로 보정 + 방향별 판정 (통제 불가 기기는 transport path별 단일 clock 대안 — 아래) |
| **C. 시간 측정이 아님** | NFR-PER-001 / 006 | 시각이 아니라 상태·양 | clock 무관 |

### 클래스 A — NFR-PER-003 (참가 후 3초 이내 문서 트리 + 접속자 목록 표시)

원인(참가 액션)과 결과(두 UI 렌더 완료)가 **같은 브라우저 탭**에서 일어난다. 관측자가 하나이므로
clock skew 문제가 애초에 생기지 않는다 — 클래스 B가 쓰는 시계 차이 보정도, ack round trip도 필요 없다.

- **도구**: 해당 페이지의 `performance.now()`. Playwright로 자동화하면 `click` → `waitForSelector`
  시간차로도 같은 값을 얻는다.
- **`Date.now()`가 아니라 `performance.now()`** — 후자는 monotonic이라 측정 도중 NTP 보정이 clock을
  건드려도 값이 튀지 않는다. 단일 clock 측정이라도 이건 지킨다.
- 6개 중 유일하게 velog 글의 "초기 로딩" 측정과 직접 대응하는 항목 — 네트워크 조건 고정 방법론을 그대로
  적용한다. 반복 횟수와 판정 통계는 아래 "공통 측정 원칙"을 따른다(20회 이상, p95).
- **샘플을 얻는 법**: 본 측정 20회차마다 G가 가입 화면에서 직접 가입하는 시간을 샘플 하나로 쓴다. 회차마다 새
  스택이라 조건이 같고, 샘플마다 새 닉네임을 써서 오프라인 멤버가 쌓이는 일도 없다. t0 = `입장` 클릭 이벤트,
  t1 = 트리에 시드 문서가 보이고 배너에 전원(`N명 접속 중`)이 표시된 뒤 double rAF. 가입 후 이동은 클라이언트
  내비게이션이라 `performance.timeOrigin`을 더한 절대 시각으로 뺀다. H는 loopback이라 진단용으로만 남긴다.

### 클래스 B — 클라이언트 간 전파 (각 1초 이내)

| 항목 | 원인 → 결과 |
|---|---|
| NFR-PER-002 | A가 블록 수정 → B 화면에 반영 |
| NFR-PER-004 | A가 채팅 전송 → B에게 전달 |
| NFR-PER-005 | 발표자가 화면 위치/스크롤 변경 → 참여자 화면에 반영 |

셋 다 원인과 결과가 **다른 머신**에서 일어난다. 두 브라우저가 각자 `Date.now()`를 찍어 빼면 실제
지연이 아니라 clock 오프셋을 재게 된다. 그리고 이 오차는 랜덤 노이즈가 아니라 **constant bias**라
반복 평균으로 지워지지 않는다 — 300ms 틀어진 clock으로 100번 재면 100번 다 300ms 틀린다.

#### 기본 방식: 하네스가 잰 시계 차이 + 마커 + 방향별 판정

1. 회차 시작과 끝, 그리고 편집·채팅 구간의 25·50·75% 지점에서 하네스(H의 orchestrator)가 두 측정 페이지의
   시계를 15번씩 왕복해 읽고, 왕복이 가장 짧은 표본으로 시계 차이 θ와 오차 u(왕복의 절반)를 구한다(Cristian
   방식). 회차 중간의 시각은 이 읽기들을 지나는 최소제곱 직선으로 θ를 보정한다. 기기별 오차 = 가장 큰 u + 직선에서
   가장 멀리 떨어진 읽기의 거리이고, 회차 오차 U는 두 기기의 합이다. 일정한 속도로 흐르는 시계는 직선 보정으로
   지워지므로 오차에 넣지 않고, 시계 점프처럼 직선을 벗어난 만큼만 넣는다(#215; 읽기가 시작·끝 둘뿐인 옛 회차는
   "큰 u + 시작·끝 θ의 차이"). U가 **10ms**를 넘는 회차는 계측 실패로 교체한다(2026-10-12 결정, #163).
   OS의 NTP 동기화에는 기대지 않는다 — 하네스는 단조 시계(`performance.now()`)를 읽어서 OS가 벽시계를 맞춰도
   바뀌지 않고, 이 방식은 기기 OS와 무관하다. 시계를 읽는 경로(제어 채널)는 열화를 걸지 않으므로 혼잡 칸에서도 U가 커지지 않는다.
2. 송신 측 페이지가 **송신 이벤트 자체의 `timeStamp`**로 `t0`을 기록한다(입력 이벤트, 전송 클릭, 발표자의 스크롤
   이벤트). 원격 조종 명령이 돌아온 뒤 시계를 읽으면 그만큼 늦게 찍힌다. 모든 항목은 **마커**로 짝을 짓는다 —
   송신 측은 `마커 → t0`, 수신 측은 `마커 → t1`을 남기고 사후에 조인한다. 제품 코드(페이로드 필드, 측정용 훅)는
   바꾸지 않는다.
   - **블록 편집(NFR-PER-002)·채팅(NFR-PER-004)**: 매 회차 고유한 마커 문자열을 입력·전송한다. 원격 편집은
     `el.value = …`로 반영되어 DOM 변화가 없으므로, 수신 측은 textarea의 `value` setter를 감싸서 마커를 감지한다.
   - **발표자 위치(NFR-PER-005)**: 전달되는 값은 스크롤 값이 아니라 anchor(`{blockId, ratio}`)라서, 기기마다 화면
     크기가 다르면 스크롤 값을 마커로 쓸 수 없다. **목표 블록**을 마커로 쓴다 — 발표자가 목표 블록을 화면 맨 위로
     옮긴 스크롤 이벤트가 `t0`, 따라가는 쪽에서 스크롤이 끝났을 때(`scrollend`) 그 블록이 맨 위 ±8px 안에 있으면
     double rAF 뒤가 `t1`이다("반영"의 정의, 2026-10-12 결정). 이동이 시작된 시각은 참고로 함께 남긴다. 발표 중
     문서 이동은 재지 않는다. 워크로드는 회차마다 편집 단계 뒤의 발표 단계다: 목표 블록 20개, 3초 간격, H가
     발표한 뒤 G가 발표한다(편집 중에는 커서가 스크롤을 움직여 따로 뗀다).
3. 수신 측이 화면 반영 완료 시점에 `t1`을 찍고, 두 시각을 θ로 한 시계에 맞춘 뒤 뺀다.
4. **A→B와 B→A를 양쪽 다 잰다.**

**합격/불합격은 항상 방향별로 따로 판정한다** — 두 방향의 평균으로 판정하지 않는다. A→B가 1400ms, B→A가
600ms면 평균은 1000ms로 "통과"처럼 보이지만, A→B를 겪는 사용자는 전원 budget을 어긴 상태다. 판정은 p95와
U를 함께 본다: p95 + U ≤ budget이면 합격, p95 − U > budget이면 불합격, 그 사이는 **판정 불가**다.

**호스트 PC가 클라이언트를 겸하면 비대칭은 설계상 정상이다**: 서버 컨테이너를 띄운 호스트 PC에서 호스트 본인도
브라우저로 참여하면, 호스트 클라이언트↔서버 구간은 LAN이 아니라 loopback이다(LAN IP로 접속해도 OS가 내부에서
처리한다). 게스트↔서버 구간만 실제 LAN을 지나므로 두 방향 값이 다른 게 당연하다. 그래서 회차마다 **토폴로지**를
측정 조건으로 기록한다.

**측정 클라이언트는 서로 다른 실기기다**: 같은 PC에 창 두 개를 띄우면 두 창이 NIC·CPU·Wi-Fi 라디오를 하나씩
공유해 기기별 차이가 드러나지 않는다. 그래서 서로 다른 기기 2대(H, G)로 잰다.

**어떤 clock을 읽나**: 페이지마다 원점이 다른 `performance.now()`가 아니라, wall clock에 고정되면서도 monotonic한
`performance.timeOrigin + performance.now()`를 쓴다. 맨 `Date.now()`는 측정 도중 OS가 시계를 보정하면 값이 튄다.

**budget 대비로 충분한가**: 단일 머신 스모크에서 U는 약 2ms였다. budget은 1000ms다(0.2%). 실기기 2대의 U는
리허설에서 10ms 한도와 대조한다.

**PTP는 쓰지 않는다**: 마이크로초급 정확도는 NIC 하드웨어 타임스탬핑과 스위치의 boundary/transparent clock 지원이
있어야 나오고, 1000ms budget에는 과하다.

#### 대안: clock을 통제할 수 없는 클라이언트 — transport path가 방법을 정한다

> v0.1.0 캠페인(데스크톱 2대)에서는 쓰지 않는다. 두 측정 브라우저를 하네스가 모두 제어하므로 위 기본 방식으로
> 충분하고, 아래 훅을 넣으면 릴리스 이미지를 그대로 잴 수 없다. 폰처럼 시계를 읽을 수 없는 기기를 넣을 때를
> 위한 대안으로 남겨둔다.

`docs/SRS-ko.md` §2.4는 **모바일 웹 브라우저를 지원 범위에 넣는다.** 폰에서는 `chronyd`를 띄울 수도,
오프셋을 읽을 수도 없다 — 내가 관리하지 않는 팀원 기기도 마찬가지다. 이때는 상대 clock을 아예 읽지
않는 방식으로 바꾼다. 다만 **어느 clock 하나로 잴 수 있는지는 그 항목의 데이터가 어느 path로 가는지가
정한다**:

| path | 항목 | 우리 코드가 relay 지점에 있는가 | 대안 |
|---|---|---|---|
| App WS (Next.js 커스텀 서버) | NFR-PER-004 채팅 | 예 — 서버가 수신자마다 `send()` | 서버 단일 clock + 렌더 ack |
| Yorkie direct (클라이언트 ↔ Yorkie) | NFR-PER-002 블록 편집, NFR-PER-005 발표자 위치 | 아니오 — 클라이언트가 `yorkie.Client`로 Yorkie에 직접 붙고(`app/(workspace)/presence-provider.tsx`), App 서버는 이 트래픽을 보지 않는다. Yorkie는 Go 서버라 instrumentation 훅을 넣을 수도 없다 | 송신 측 단일 clock round-trip echo |

##### App WS path (NFR-PER-004): 서버 단일 clock + 렌더 ack

1. 서버가 relay할 때 자기 clock으로 `T0`을 찍는다 — **그 수신자에게 `send()` 하기 직전에.** 8명에게
   루프로 broadcast하면 마지막 수신자는 첫 수신자보다 늦게 나가므로 수신자별로 따로 찍어야 한다.
2. 수신 클라이언트가 화면 반영 후 가벼운 ack를 되쏜다(아래 rAF 주의).
3. 서버가 ack 도착 시각 `T1`을 **역시 자기 clock으로** 찍는다.

두 시각이 서버 프로세스의 한 clock에서만 나오므로 skew가 소멸한다. 단, `T1 - T0`은 **downlink + 렌더 +
uplink**이라 사용자가 겪지 않는 uplink hop이 섞여 있고 A의 입력~서버 구간은 빠져 있다. 서버가 A의 op를
받은 시각 `T_in`도 함께 찍어 `T1 - T_in`을 쓰면 누락 구간이 "A의 로컬 입력 처리 + A→서버 네트워크"로
줄어든다.

구현 시: 전송마다 correlation id를 실어 서버가 `id → T0` 맵으로 ack를 매칭한다. 서버 쪽 시각도
`Date.now()`가 아니라 `process.hrtime.bigint()`를 쓴다 — 단일 머신이라도 NTP 보정이 wall clock을 점프시킬
수 있다. 이 ack instrumentation은 **측정 모드에서만 켜지는 훅**이고 프로덕션 빌드에 남으면 안 된다.

##### Yorkie direct path (NFR-PER-002/005): 송신 측 단일 clock round-trip echo

relay 지점이 없으니 clock을 **송신 클라이언트 A** 쪽 하나로 모은다.

1. A가 편집(또는 스크롤)하는 순간 `performance.now()`로 `t0`을 찍는다. 마커는 기본 방식 2단계와 같다.
2. B가 그 변경을 화면에 반영하면(double rAF, 아래) 측정 모드 전용 presence 필드에 그 마커를 실어 에코한다.
3. A가 `doc.subscribe("others")`로 에코를 받는 순간 `t2`를 찍는다.

`t2 - t0` = A→B one-way + B 렌더 + B→A one-way다. 판정은 **보수적으로만** 한다:

- `t2 - t0 ≤ 1000ms`면 그 안에 든 one-way(A→B + 렌더)도 당연히 1000ms 이하 — **합격**.
- `t2 - t0 > 1000ms`면 one-way가 budget 안인지 밖인지 이 값만으로는 알 수 없다 — **판정 불가**. clock을
  통제할 수 있는 기기로 기본 방식을 다시 돌려 판정한다.

에코 역시 ack와 같은 **측정 모드 전용 훅**이고 프로덕션 빌드에 남으면 안 된다.

#### "화면 반영 완료" 시점을 잡는 법 (모든 방식 공통)

`requestAnimationFrame` 콜백은 그 프레임이 **페인트되기 직전**에 실행된다. 그 안에서 시각을 찍으면
페인트 전을 재는 것이다. 페인트 이후를 잡으려면 **double rAF**를 쓴다:

```js
requestAnimationFrame(() => requestAnimationFrame(() => markRendered(id)));
```

두 번째 콜백은 다음 프레임의 시작이고, 그 시점엔 이전 프레임이 이미 화면에 나가 있다.

rAF는 **백그라운드 탭에서 멈춘다.** 측정 중인 탭은 항상 foreground여야 하고, 클라이언트마다 별도 창을
쓴다 — 한 창에 여러 클라이언트를 탭으로 띄우면 뒤에 깔린 탭은 rAF가 돌지 않아 `t1`이 찍히지 않거나
탭이 다시 앞에 나올 때까지 밀려 찍힌다.

#### 렌더 시간만 분리하고 싶을 때 — 진단용이지 판정용이 아니다

아무 작업 없이 즉시 에코만 하는 ping/pong을 같은 방식으로 재 `T_network`를 얻고 빼면 클라이언트 렌더
처리 시간이 근사된다. 두 가지를 지킨다:

- **합격/불합격 판정은 뺄셈하지 않은 값으로 한다.** 뺄셈은 "시간이 어디서 갔나"를 보는 진단이다.
- ping 페이로드가 실제 블록 op보다 훨씬 작으면 두 홉 비용이 같다는 가정이 약해진다 — 크기를 맞추거나
  근사임을 명시한다.

### 클래스 C — NFR-PER-001 / 006

시각을 재는 항목이 아니라서 clock 논의가 적용되지 않는다.

| 항목 | 재는 것 | 도구/방법 |

NFR-PER-001은 독립 항목이라기보다 **나머지 다섯 개를 감싸는 조건**으로 취급한다 — "8명 부하 하에서도
002/003/004/005가 여전히 기준을 만족하는가"가 실제로 묻는 것이다. NFR-PER-006은 "일반적인 협업
환경"이 무엇인지부터 시나리오로 못박아야 측정이 재현 가능해진다.

**NFR-PER-001 판정 기준 (2026-10-12 결정, #163)**:

- **실패 조건**: 셋 중 하나만 걸려도 그 회차는 실패로 판정한다.
  - 세션 중 연결이 끊기는 클라이언트가 1개라도 발생. 연결은 **두 개**다 — App WS(채팅)와 Yorkie 스트림.
    Yorkie SDK는 WebSocket이 아니라 HTTP 기반 Connect/gRPC-web 스트림을 쓰므로 WS 끊김만 보면 문서 동기화
    쪽 끊김을 놓친다. 앱 내부 이벤트는 하네스가 볼 수 없으므로, Yorkie 쪽은 CDP로 Watch 스트림의 종료를
    관측하고(`e2e/network.ts`와 같은 방식) WS는 close 이벤트를 센다. 측정 클라이언트의 `⚠ 연결 끊김` 배지도
    실패로 센다.
  - 활동 종료 후 CRDT 상태가 모든 클라이언트에서 동일 내용으로 converge하지 않음. 편집 마커가 최종본에,
    채팅 마커가 H·G의 채팅 목록에 정확히 한 번씩 있는지도 확인한다.
  - 시나리오상 **예상하지 않은** 에러 응답(HTTP 4xx·5xx 또는 WS 에러 프레임)이 1건 이상 발생. 정상 동작인
    4xx(세션 만료 401, 업로드 한도 초과 413 등)는 세지 않는다 — 이 워크로드에서 그런 응답이 나올 path가
    있다면 회차 시작 전에 목록으로 적어둔다.
- **세션 길이**: 8명 동시 접속 상태로 **10분** 고정.
- **사용자당 워크로드**: 10분 동안 블록 편집 **20회**, 채팅 전송 **10회**를 버스트 없이 고르게 분산.
- **반복**: 20회 이상, **20회 중 실패 0건이어야 통과**. 이 항목은 발생 여부 판정이라 p95를 적용하지
  않는다. 0/20이 보장하는 범위도 기록해둔다 — rule of three에 따라 n회 중 0건이면 95% 신뢰로 실패율이
  `3/n` 미만, 즉 0/20은 "실패율 15% 미만"까지만 말해준다. 더 강한 주장이 필요하면 n을 늘린다.
- **비용**: 10분 × 20회 = 최소 200분, 기기(또는 헤드리스 세션) 8개. 회차 사이 초기화 시간은 별도다.
  (일정상 부담되면 회차 수를 줄이는 대안이 있다. 다만 줄인 만큼 보장 범위가 넓어지므로 — 0/10이면
  "실패율 30% 미만" — 보고서에 그 `3/n` 값을 같이 적는다. 현재 기준은 20회 유지다.)

**NFR-PER-006 판정 기준 (2026-10-12 결정, #163)**: "일반적인 협업 시나리오"를 NFR-PER-001과 같은
워크로드(세션 10분, 블록 편집 20회, 채팅 10건)로 고정하고 **파일 블록은 제외**한다 — 파일 업로드/뷰어의
메모리는 이 시나리오가 다루는 문제가 아니라서다. 측정값은 세션 전체의 **피크 메모리**이고,
`docs/SRS-ko.md`의 500MB threshold와 직접 비교한다.

- **무엇을 읽나**: Chrome 작업 관리자의 해당 탭 **"Memory footprint"**. 이것은 DOM 노드를 포함한 OS
  메모리고, 옆의 "JavaScript memory"는 JS 힙만이다. SRS의 "클라이언트 메모리 사용량"에 가까운 건 전자다.
- **피크를 잡는 법**: 세션 내내 10초 간격으로 샘플링해 최댓값을 쓴다. 하네스가 각 측정 브라우저의 CDP로
  memory-infra trace를 걸어, Chrome이 직접 보고하는 렌더러의 private footprint(작업 관리자의 "Memory
  footprint"와 같은 값)를 받는다. 원격 G에서도 같은 방식이라 OS별 샘플러가 필요 없다. 첫 리허설에서 기기마다
  작업 관리자 값과 한 번 대조한다. trace 시작 뒤에 생긴 렌더러는 이름이 `"Renderer"`가 아니라 명령줄
  (`--type=renderer`)로 찍힌다.
- **반복**: NFR-PER-001과 **같은 세션에서** 함께 재므로 회차 수도 001을 따른다(20회). 회차·측정
  클라이언트마다 피크를 하나씩 남기고, 위 문장대로 각 피크를 500MB와 직접 비교한다.
- **heap snapshot은 판정에 쓰지 않는다.** JS 힙만 세고, 스냅샷을 찍기 전에 GC를 강제하므로 찍힌 값이
  피크보다 작게 나온다. 값이 기준에 근접하거나 세션 동안 계속 오르면 그때 leak 진단용으로 쓴다.
- **`performance.measureUserAgentSpecificMemory()`는 쓸 수 없다** — secure context(HTTPS)와 cross-origin
  isolation(COOP/COEP)이 필요하고 아직 실험 기능이다. 이 앱은 LAN에서 HTTP로 돈다.
- **측정 브라우저**: 데스크톱 Chrome으로 고정한다. 모바일은 탭 단위 OS 메모리를 읽을 도구가 마땅치
  않아 판정을 보류하고, 필요해지면 방법부터 따로 정한다.

## 공통 측정 원칙

velog 글의 방법론에서 계승한 것 + 위 논의에서 추가된 리그 조건:

1. **측정 조건을 문서에 고정한다** — 참가자 수, 네트워크(LAN Wi-Fi 대역 vs 유선, 아래 프리셋, 공유 Wi-Fi면 그
   시간대와 대략의 다른 사용자 수), 브라우저,
   호스트 하드웨어 사양, 토폴로지(호스트=서버+클라이언트 / 서버 전용 기기), 그리고 클래스 B를 쟀다면 **그
   회차의 시계 오차 U**(하네스가 회차마다 기록). 조건이 매번 다르면 숫자를 비교할 수 없다. 서버는 `pnpm dev`가 아니라 실제
   배포 형태인 컨테이너로, 하네스가 회차마다 릴리스 이미지(digest 고정)를 띄운다.
2. **테스트 리그는 물리적으로 분리된 기기 2대 이상을 실제 LAN 위에서 쓴다** — 네트워크 네임스페이스로
   분리한 프로세스도 대안. 클라이언트를 전부 한 머신에 몰아두면 네트워크 비용이 0에 수렴해 숫자가
   무의미해진다. **클래스 A도 예외가 아니다** — 서버가 localhost면 3초 기준을 검증한 게 아니다.
   (clock skew 대책과는 별개 문제다. ack 방식을 쓰든 안 쓰든 이 조건은 따로 필요하다.)
3. **판정 통계는 p95로 통일한다** — 평균은 tail latency를 가리고, 중앙값은 절반의 사용자만 보장한다.
   p95를 budget과 비교해 합격/불합격을 정한다. 평균/중앙값은 참고용으로 함께 기록해도 되지만 판정에는
   쓰지 않는다. 단일 실행값은 기준으로 인정하지 않는다. "20회"가 무엇을 세는지는 클래스마다 다르다:
   - **클래스 A(003)**: 한 회차가 샘플 하나다 → **20회 이상** 반복(본 측정 20회차의 G 가입).
   - **클래스 B(002/004/005)**: 한 회차(세션)에 마커 샘플이 수십 개 나온다 → 회차를 **5~10회** 반복하고
     샘플을 **풀링해 p95**를 낸다(풀링 샘플 20개 이상). 회차별 p95도 함께 기록해 회차 간 편차를 본다.
   - 샘플이 20개를 밑돌면 p95를 내지 않는다(5~10개로는 p95 자체가 무의미하다).
   - **p95는 시도 기준이다.** 시간 안에 보이지 않은 샘플(002·004·005는 10초, 003은 30초)은 ∞로 친다. 도착한
     샘플만 모으면 실제보다 빠르게 보이기 때문이다. 시도·관측·타임아웃·불일치·중복 건수를 함께 보고한다.
   - **percentile 계산은 nearest-rank**로 통일한다 — 오름차순 정렬 후 `⌈0.95 × n⌉`번째 값. n=20이면 19번째다.
     도구마다 interpolation 방식이 달라 같은 데이터에서 다른 p95가 나오므로 방식을 고정한다.
4. **측정 도구는 재는 대상에 맞춰 고른다** — 클래스가 이미 이걸 결정한다. Lighthouse류는 페이지 로드
   프로파일러라 클래스 B(정상 작동 중 sync latency)에는 맞지 않는다.
5. **현재 베이스라인(최적화 전 숫자)을 먼저 기록한다** — 지금 통과/실패 여부와 여유/부족분을 먼저
   알아야 `ROADMAP.md` Phase 5에서 무엇을 고칠지 우선순위를 매길 수 있다.

## 측정 조건 매트릭스

보고서의 결과 표는 "이 조건에서 이 숫자"다. 조건은 두 축으로 잡는다.

| 축 | 값 |
|---|---|
| 동시 사용자 | 2 / 4 / 8명 |
| 네트워크 | 아래 시나리오 프리셋 4종 |

12칸을 전부 채우는 게 부담스러우면 "8명 × 네트워크 4종"과 "baseline × 사용자 3종"(겹치는 칸 하나)
6칸으로 줄인다. 앞쪽은 네트워크가 나빠질 때, 뒤쪽은 사람이 늘 때 숫자가 어떻게 변하는지를 보여준다.

**칸별 회차 수와 SRS 판정 칸**:

- **SRS 합격/불합격은 "8명 × baseline" 한 칸에서 판정한다.** SRS의 threshold는 network degradation 조건을 정하지
  않으므로 baseline이 그 threshold를 재는 칸이다. NFR-PER-001(20회 중 실패 0건)과 006은 이 칸에서 20회를 돌리고,
  같은 20회차의 마커 샘플이 002/004/005의 풀링 p95도 겸한다. NFR-PER-001 절의 "200분" 비용은 이 한 칸 기준이다.
- **나머지 칸은 판정이 아니라 보고다** — "이 조건에서 이 숫자". 칸마다 클래스 B 규칙(공통 측정 원칙 3)대로
  5~10회차를 돌려 샘플을 풀링해 p95를 낸다. NFR-PER-001의 실패 조건(끊김·convergence 실패·예상 밖 에러)은 이
  칸들에서도 관측해 건수를 기록하지만, 0/20은 요구하지 않는다.

### 시나리오 프리셋 (2026-10-12 결정, #163; light는 2026-10-13 평시 실측으로 변경)

값은 모두 **왕복 기준**이다(ping이 왕복을 재기 때문).

| 시나리오 | RTT 추가 | 손실 | 대역폭 |
|---|---|---|---|
| baseline(혼잡 없음) | +0ms | 0% | 제한 없음 |
| light | 학교 Wi-Fi 평시 실측값. 없으면 +40ms | 실측값. 없으면 1% | 실측값(상한). 없으면 제한 없음 |
| moderate | 학교 Wi-Fi 혼잡 실측값. 없으면 +120ms | 실측값. 없으면 3% | 실측값(상한). 없으면 제한 없음 |
| heavy | +300ms | 10% | 제한 없음 |

**light와 moderate는 학교 Wi-Fi를 재서 LAN에 재현한다** — light는 사람이 적은 평소 시간대, moderate는 사람이 많은
시간대의 값이다. 서비스를 학교 Wi-Fi에서 직접 시험하지 않는다. RMF-Block
트래픽은 WAN을 지나지 않으므로, 혼잡한 학교 Wi-Fi에서 느려지는 곳은 기기와 AP 사이 무선 구간이다. 그래서
두 시간대에 각각 학교 Wi-Fi에서 게이트웨이까지의 RTT·jitter·손실과 대역폭(공개 iperf3 서버나 speed test,
WAN이 섞이므로 상한값)을 재고, 측정 네트워크(아래 "부하 구성")에서 G에 지연 = 학교 RTT − 측정 네트워크 기본
RTT, 손실·대역폭 = 실측값으로 건다. 학교 Wi-Fi는 기기 간 통신을 막는 경우(client isolation)가 많아 서비스를 직접
띄울 수도 없다. 그 시간대에 잴 수 없으면 위 대체값을 쓰고 "실측 아님"으로 표시한다.

### degradation을 거는 방법

| 측정 클라이언트(G) OS | 도구 |
|---|---|
| Windows | [Clumsy](https://jagt.github.io/clumsy/) — 필터 양방향, Lag·Drop·Bandwidth |
| macOS | 내장 `dnctl` + `pfctl` — 보내는 쪽·받는 쪽 pipe 두 개 |
| Linux | `tc netem` — 송신은 `prio` + u32 필터, 수신은 `ifb`로 돌려서 |

명령은 [`docs/perf/runbook-ko.md`](perf/runbook-ko.md) §12에 있다.

- **G에만 건다.** 서버 기기(H)에 걸면 background 사용자와 H 자신의 트래픽까지 느려진다. H의 측정 브라우저는
  loopback으로 서버에 붙으므로 어떤 NIC 설정으로도 열화가 걸리지 않는다 — 결과에 "H는 baseline"으로 남긴다.
- **H의 3000·8080 포트로 오가는 트래픽만** 거른다. G의 브라우저 서버(하네스 제어 채널)가 느려지면 측정 시각
  자체는 브라우저 안에서 찍더라도 워크로드 간격이 밀리고, 시계 보정 오차 U가 커지고, 손실이 크면 하네스가 G와의
  연결을 잃는다. 그래서 시스템 전체에 걸리는 도구(macOS Network Link Conditioner, Chrome DevTools throttling)는
  쓰지 않는다.
- **양방향에 절반씩 건다.** 서버가 G로 보내는 방향(H→G)과 G가 보내는 방향(G→H)이 모두 무선을 지난다. 한쪽에만
  걸면 다른 방향은 열화 없이 재진다. 방향마다 지연 = RTT 추가 ÷ 2, 손실 = 손실 ÷ 2, 대역폭 = 그대로.
- **적용 여부는 ping으로 확인하지 않는다.** ICMP는 포트 필터에 걸리지 않는다. 하네스가 G에서 재는 HTTP RTT
  probe(회차마다 기록)로 확인한다.

## 부하 구성

목표 규모가 8명 이하라서 이 load test는 "요청을 최대한 퍼붓기"가 아니라 **8명이 평소처럼 쓰는 상황을
재현하고 그 아래에서 지연·자원을 재는 것**이다. 그래서 k6·JMeter 같은 HTTP 부하 도구는 쓰지 않는다 —
Yorkie는 HTTP 스트림 위에서 CRDT 상태를 주고받으므로, 요청을 되풀이해 쏘는 것으로는 실제 동작이
재현되지 않는다.

### 클라이언트의 두 역할

| 역할 | 정체 | 하는 일 |
|---|---|---|
| **측정 클라이언트** | H와 G, 서로 다른 실기기 2대의 데스크톱 Chrome | 002/003/004/005 지연과 006 메모리를 잰다 |
| **background 사용자** | H에서 측정 Chrome과 다른 프로세스로 도는 headless 브라우저 컨텍스트(E2E 픽스처 `users.join`) | 편집·채팅만 한다. 측정하지 않는다 |

- 기기가 2대뿐이라 나머지 사용자는 H에 둔다. 실제 클라이언트 코드 경로(presence heartbeat 포함)를 그대로 타고,
  사용자당 2분에 편집·채팅 3회 정도라 부하가 가볍다. H의 CPU와 `docker stats`를 함께 기록해 포화 여부를 본다.
- 측정 네트워크는 인터넷이 되고 기기 간 통신을 막지 않는(client isolation 없음) Wi-Fi 하나다. H와 G를 같은
  SSID에 붙이고, RMF-Block 트래픽은 그 LAN 안에서만 오간다(2026-10-16 변경, 팀 합의. 이전 계획은 리눅스 노트북의
  오프라인 핫스팟이었다). 인터넷이 되므로 운용을 Claude Code에 맡길 수 있다(runbook §7.1). 같은 Wi-Fi의 다른
  트래픽은 통제하지 않고 조건으로 기록한다(공통 측정 원칙 1). 혼잡은 이 위에서 G에 일부러 건다(위 "degradation을
  거는 방법").
- G는 브라우저 서버만 띄우고, H의 orchestrator가 원격으로 조종한다(`pnpm perf:browser` → `PERF_G_WS`). 결과·시계·
  워크로드·리셋이 H 한 곳에 모인다.
- 메모리(006)는 실제 브라우저 탭에서만 의미가 있으므로 측정 클라이언트에서만 잰다.

### 고정하는 것

- **워크로드**: NFR-PER-001의 사용자당 워크로드를 고정 간격·고정 순서로 보낸다(난수 없음). 발표 단계는 위 클래스 B.
- **시작 문서와 입력 문안**: 회차마다 H가 블록 60개짜리 시드 문서를 만들고, 마커 형식이 고정이다. 채팅 기록은
  빈 상태로 시작한다 — 채팅 저장이 메시지 파일 전체를 다시 쓰므로 기록이 쌓이면 지연이 늘어나기 때문이다.
- **매 회차를 새 볼륨에서 시작한다**: 회차마다 일회용 Compose 프로젝트를 띄우고 끝나면 볼륨째 지운다. 컨테이너
  재시작만으로는 앱 데이터(`.data/`)와 Yorkie/Mongo 문서가 남는다. 앱 이미지는 v0.1.0 digest로 고정한다.

### 서버 쪽 숫자도 같이 남긴다

SRS 기준은 클라이언트 관점이지만, `docs/SRS-ko.md` §2.4가 미뤄둔 질문("호스트 컴퓨팅 자원에 의존")에
답하려면 그 순간 호스트가 얼마나 바빴는지가 필요하다. 매 회차 `docker stats`로 app·Yorkie·MongoDB
컨테이너의 CPU·메모리를 5초 간격으로 기록해 그 회차 결과 옆에 저장하고, 호스트 사양을 함께 적는다.
호스트로 쓸 수 있는 기기가 2종 이상이면(예: 고사양·저사양 노트북) 8명 본 측정을 두 기기에서 돌린다.

**관측 스택(#192)은 원인을 설명할 뿐 판정하지 않는다.** 관측 스택 기준 칸과 혼잡·단절 칸에서만 켠다
(`pnpm perf:observe` + `PERF_OBSERVE=1`, 절차는 운용 가이드 §14).
- **구성**: Prometheus 3.5.0, cAdvisor 0.52.1, Grafana 12.1.1(`e2e/perf/observe/`). 측정 내내 떠 있고, 하네스가 회차마다
  그 회차 네트워크에 붙였다 뗀다. 수집 간격은 `docker stats`와 같은 5초다.
- **지표**:
  - 컨테이너 CPU·메모리(cAdvisor);
  - Yorkie `/metrics`(프로파일링 리스너 8081, LAN에 열지 않음)의 RPC 처리 수·실패, PushPull·RPC 응답 시간 p95.
- **Docker Desktop 제약**: cAdvisor가 엔진의 이미지 저장소를 읽지 못해 컨테이너 이름을 모른다. 그래서 cgroup을
  직접 읽고, 하네스가 회차마다 컨테이너 ID에 이름을 붙인다. 이 방식에서는 컨테이너별 네트워크가 나오지 않으므로
  네트워크는 `docker stats` 기록에서 본다.
- **대시보드**: Grafana(H의 `127.0.0.1:3300`)에 하네스가 회차의 측정 구간·단절·복구 시각을 주석으로 남긴다.
- **오버헤드**: 관측 스택 기준 칸과 판정 칸(관측 끔)의 차이를 회차 간 변동과 함께 서술로만 보고한다. 켤지 말지를
  가르는 임계값은 두지 않는다.

### 재연결 (FR-022-12 · UC-022) — 참고 측정

NFR-PER 항목은 아니지만 network degradation 상황의 성능을 보여주는 데 필요하다. 회차는 약 5분짜리 전용
프로토콜이다(`PERF_OUTAGE=20|40`): 작업 → G만 단절 → 복구 → 실패한 채팅 재전송 → 작업 → 수렴 확인. 20초를
기본으로, 30초 grace period(`docs/SRS-ko.md` UC-022 비고)를 넘는 40초를 진단용으로 둔다. 이 회차의 숫자는 지연
p95와 비교하지 않는다.

- **단절 방법**: 하네스가 G 브라우저의 Yorkie 스트림을 끊고 앱 소켓을 닫는다(`e2e/network.ts`의 `networkProbe`).
  연결이 실제로 끊겼음이 기록에 남는다. Wi-Fi를 끄면 G의 제어 채널까지 끊기므로 쓰지 않는다. 포트를 100% 버리는
  blackhole은 보조 실험이다 — TCP 연결이 살아남아 "재연결"이 아니라 "정지"가 될 수 있으니 어느 쪽이었는지 기록한다.
- **재는 것**: 경로별(문서, 채팅, 세션 알림) 복구 시간, 끊긴 동안 입력한 문안이 최종본에 정확히 한 번 나타나는지.
- **채팅은 세 경우를 따로 기록한다**: ① H가 보낸 메시지를 G가 재연결 뒤 정확히 한 번 받는지(백필), ② G가
  오프라인에서 보낸 메시지가 실패로 표시되는지, ③ `전송 실패 · 다시 보내기`를 눌렀을 때 전달·중복 여부. 앱은
  오프라인 메시지를 자동으로 다시 보내지 않으므로(UC-060 E1-1) ③은 자동 복구로 세지 않는다.
- 세션 알림 소켓은 재연결하지 않는 것이 알려진 실패다(#37). 실패로 기록하되 건너뛰지 않는다.

### 이 비교가 실제로 재는 것

RMF-Block 서버는 호스트의 LAN 안에 있고, Notion/Google Docs는 반드시 인터넷을 거친다. 같은 도서관
와이파이에 붙어 있어도 RMF-Block 트래픽은 "기기 → AP → LAN 서버"만 congestion 구간을 지나가는 반면
Notion/Google Docs는 "기기 → AP → 도서관 uplink → 인터넷 → 클라우드"까지 전부 지나간다. 이 실험은
그 구조적 차이가 실제 체감 성능 차이로 이어지는지 검증하는 것이지 우연한 비교가 아니다 — 보고서·
발표에 이 문장을 그대로 명시해야 결과 해석이 정확해진다. 선행 연구도 같은 단서를 단다 — Google Docs와
자체 에디터(MUTE)를 같은 방법으로 잰 [Dang & Ignat (IFIP Networking 2016)](https://ieeexplore.ieee.org/document/7497258/)은
"MUTE는 로컬 서버, Google Docs는 원격 서버에서 쟀으므로 차이의 일부는 구조 때문"이라고 명시한다.

두 가지를 함께 적는다:

- **구조적 이점(uplink·인터넷 구간)은 실측(아래 A)에서만 드러난다.** 에뮬레이션(아래 B)은 세 도구에
  같은 degradation을 더하므로 AP 구간 degradation에 대한 내성만 비교한다 — uplink congestion은 재현하지 않는다.
- 따라서 결론도 둘로 나눈다: "실측 도서관 조건에서 X가 더 빨랐다"(A)와 "같은 AP 구간 degradation에서 X가 더
  잘 버텼다"(B). B의 결과를 A의 주장처럼 쓰지 않는다.

### 조건 재현 방법 두 가지

**A. 실측 (in-situ measurement, 권장)** — 시험기간 도서관에서 `ping`/`iperf3`로 실제 RTT·jitter·packet
loss·대역폭을 잰다. `ping`은 **LAN 서버와 클라우드 쪽(예: 각 서비스 도메인) 양쪽에** 대해 잰다 — 두 값의
차이가 위에서 말한 구조적 차이의 크기다. 숫자는 그 회차의 측정 조건으로 남기고, B의 파라미터로도
그대로 쓴다. "측정 조건을 문서에 고정한다"는 위 공통 측정 원칙 그대로 — 임의의 숫자를 쓰면 재현
불가능하다.

**B. 통제된 네트워크 에뮬레이션** — **세 도구에 똑같이 걸리는 지점에만** 적용한다. 즉 측정 클라이언트
머신 자체이거나, 모든 트래픽이 지나는 Linux 게이트웨이(AP 뒤에 둔 라우터)다. 도구 표와 DevTools
throttling의 한계는 본문 "측정 조건 매트릭스 › degradation을 거는 방법"으로 옮겼다.

- **RMF 서버(App/WS Server, Yorkie)에 `tc netem`을 거는 방식은 경쟁 비교에 쓰지 않는다.** RMF-Block만
  느려지고 Notion/Google Docs는 영향을 받지 않아 비교가 한쪽으로 기운다. RMF-Block 단독 NFR 측정에서
  조건을 재현할 때만 쓴다.
- 세 도구 모두 **웹 버전**으로 잰다 — 데스크톱 앱은 DevTools throttling과 아래 하네스의 스크립트 주입이
  닿지 않는다.

A로 잰 실측값을 B의 파라미터로 주입하는 조합이 가장 신뢰도 높다.

### 시나리오 프리셋

본문 "측정 조건 매트릭스 › 시나리오 프리셋"으로 옮겼다(거기서 "A(실측)"은 "실측"으로 읽는다).

### 태스크 설계

"애국가 1·2절 교대 입력" 하나만으로는 순차 편집 패턴밖에 못 본다. 아래 5개를 세트로 구성해 각기
다른 협업 패턴을 커버한다 — 전부 세 도구(RMF-Block/Notion/Google Docs) 동일 조건에서 반복 가능한
것만 골랐다. 각 태스크는 세 도구 모두에서 반복하고, 텍스트 길이·구조와 각 사용자가 입력할 문안은
도구 간 고정한다.

| # | 태스크 | 관찰 대상 |
|---|---|---|
| 1 | **순차 교대 입력**(원안 — 애국가 1·2절, A/B가 한 줄씩). 1절은 A 선공/B 후공, 2절은 B 선공/A 후공으로 **순서 카운터밸런싱**해 타자 속도 편차를 상쇄한다(within-subjects counterbalancing) | 기본 propagation latency·체감 완료 시간 |
| 2 | **동시 충돌 편집** — 같은 문단/같은 줄을 A·B가 동시에 수정 | 충돌 해소·병합 동작 — CRDT(RMF-Block) vs Google Docs의 OT vs Notion 자체 알고리즘이 congested network에서 다르게 깨지는지 |
| 3 | **자유 동시 편집** — 턴 강제 없이 각자 원하는 위치에 5분간 자유롭게 타이핑해 문서 하나를 공동 완성 | 순서를 강제하지 않는 실제 사용 패턴에 더 가까운 지연·유실·중복 |
| 4 | **파일/이미지 삽입 포함** — 텍스트 입력 중간에 이미지 1~2개 첨부(세 도구 모두 같은 파일) | 텍스트보다 무거운 payload가 congested network에서 업로드·동기화에 걸리는 시간 |
| 5 | **편집 중 단절→재연결** — 편집 도중 한쪽 클라이언트만 네트워크를 **20초** 끊었다가 복구(선택: 40초 회차 추가) | resync 시간·데이터 유실 여부. 20초/40초 선택 근거는 본문 "재연결"로 옮겼다. 세 도구 모두 오프라인 편집 후 재연결 시 병합 동작이 달라 회복력 비교에 적합 |

시나리오(위 표)마다 태스크 5개를 전부 돌리는 건 시간상 무리이므로, 태스크 1(원안)은 전 시나리오
반복하고 태스크 2~5는 "moderate congestion(도서관 목표값)" 시나리오 하나에서 3개 도구만 비교해도 된다 —
어디까지 돌릴지는 팀이 시간 budget에 맞춰 정할 것(제안일 뿐, 팀 미합의).

### propagation latency 하네스 — instrument할 수 없는 도구를 같은 방법으로 재기

Notion/Google Docs에는 클래스 B처럼 페이로드에 `t0`을 싣거나 에코 훅을 넣을 수 없다. 그래서 세 도구
모두 **바깥에서** 같은 방법으로 잰다 — Dang & Ignat(2016)이 Google Docs·Etherpad 지연을 잰 방식이다:

1. **Writer와 Reader를 같은 PC에서** 각자 별도 브라우저 창(도구마다 서로 다른 계정으로 로그인해 둔 별도
   프로필)으로 띄운다. 두 창이 **한 머신의 clock**을 쓰므로 NTP도, clock skew 대책도 필요 없다. 서버는
   다른 호스트(RMF 서버 또는 클라우드)에 있으므로 공통 측정 원칙 2(물리 분리)도 충족한다.
2. Playwright가 Writer 창에서 회차마다 고유한 **마커 문자열**을 입력하고, 마지막 키 입력 직후
   `performance.timeOrigin + performance.now()`로 `t0`을 찍는다.
3. Reader 창에는 Playwright로 스크립트를 주입해 둔다(`page.addInitScript`). 문서 영역의
   `MutationObserver`가 마커의 등장을 감지하면 double rAF 뒤 같은 식으로 `t1`을 찍는다. 이미지(태스크 4)는
   `<img>`의 `load` 이벤트 뒤 double rAF로 찍는다.
4. `t1 - t0`이 그 마커의 propagation latency다. 마커는 일정 간격(예: 2초)으로 회차당 수십 개를 넣는다.

- **RMF-Block도 이 하네스로 잰다.** 클래스 B의 내부 훅으로 잰 숫자를 Notion/Google Docs의 하네스 숫자와
  한 표에 놓으면 측정 방법이 달라 비교가 성립하지 않는다.
- 두 창 모두 화면에 보이도록 나란히 배치한다 — 가려진 창도 rAF가 멈출 수 있다. Chromium은
  `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding`로 띄운다.
- 동시 사용자 부하를 더하려면 논문처럼 무작위 문자열만 입력하는 **DummyWriter**를 추가한다(8명 규모는
  NFR-PER-001과 맞춘다).

### 측정 지표

| 지표 | 방법 | 역할/근거 |
|---|---|---|
| **propagation latency** | 위 하네스(Writer/Reader, 같은 PC) | **주 판정 지표.** 방법 근거: [Dang & Ignat, "Performance of real-time collaborative editors at large scale: User perspective" (IFIP Networking 2016)](https://ieeexplore.ieee.org/document/7497258/) — Google Docs는 동시 사용자 10명 안팎까지는 양호하고 그 이후 지연이 불안정해졌다 |
| 파일 업로드 반영 지연 | 첨부 시작~상대 화면에 이미지 표시 완료(태스크 4, 하네스 3단계의 `<img>` 방식) | RMF-Block 파일 블록 기능(FR-022-13/14) 포함 검증 |
| 유실/중복 | 각 사용자가 입력하기로 한 문안이 최종본에 **정확히 한 번** 나타나는지 대조해 유실 수·중복 수를 센다(태스크 2·3) | 결과(최종 문서)의 품질을 본다 — "같은 줄을 동시에 건드린 횟수"는 사용자 행동을 세는 것이라 도구 차이를 보여주지 않는다. 참고: [Ignat et al., "Studying the Effect of Delay on Group Performance in Collaborative Editing" (CDVE 2014)](https://link.springer.com/chapter/10.1007/978-3-319-10831-5_29) — Etherpad에 지연을 주입하고 최종 문서의 redundancy·error rate로 영향을 쟀다 |
| 재연결·끊김 횟수 / resync 시간 | 세션 중 드롭 여부 및 복구까지 걸린 시간(태스크 5) | NFR-PER-001과 같은 방식으로 관측. RMF-Block은 UC-022의 30초 grace period와 대조 |
| 총 소요시간(사람) | 사람 참가자가 태스크 시작~완료를 스톱워치로 잰 값 | **보조 지표(체감).** 사람의 타자·반응 편차가 수십~수백 ms 수준의 네트워크 차이를 덮으므로 판정에 쓰지 않는다. 태스크 1의 카운터밸런싱은 유지 |
| (선택) 체감 사용성 | SUS 설문 또는 NASA-TLX 워크로드 설문 | 협업 에디터 사용자 연구에서 널리 쓰이는 정성 지표 |

### 반복·통계

공통 측정 원칙 3("20회 이상, p95")을 지표별로 이렇게 적용한다:

- **propagation latency(하네스)**: 회차당 마커 샘플이 수십 개 나오므로, 회차를 5~10회 반복하고 **샘플을 풀링해
  p95**를 낸다(풀링 샘플 20개 이상 — 원칙 3의 조건 충족). 회차별 p95도 함께 기록해 회차 간 편차를 본다.
- **총 소요시간(사람)**: 사람이 하는 회차는 현실적으로 5~10회가 한계라 p95가 사실상 최댓값이 된다 —
  **원칙 3의 예외로** 중앙값 + 최소/최대를 쓰고 원자료를 전부 병기한다.
- 결과는 "RMF-Block vs Notion vs Google Docs" 표로 시나리오별로 제시한다. 단일 실행값은 근거로 인정하지
  않는다는 원칙은 그대로 적용한다.

## Vitest가 맡는 것 / 맡지 않는 것

레포에는 이미 Vitest + `@testing-library/react`가 있고 `docs/testing.md`가 5개 레이어(다섯 번째가 Playwright E2E)를 정의한다.
여기서 경계를 명시해둔다.

**wall clock 숫자는 Vitest에서 재지 않는다.** 두 가지 구조적 이유가 있고, 둘 다 설정을 바꿔서 해결할
문제가 아니다:

- DOM 환경이 happy-dom이라 **페인트가 존재하지 않는다** (ADR-004 §3). `render()`가 주는 건 DOM
  트리지 렌더된 프레임이 아니므로, "사용자 화면에 반영된 시점"을 정의할 수가 없다.
- `vitest.config.mts`가 `pool: "forks"`이고 워커 수가 머신 코어에 따라 변한다(설정 주석이 직접
  경고한다). 타이밍 노이즈가 신호를 덮는다.

여기에 ms assertion을 넣으면 `.githooks/pre-push`와 CI에서 흔들리는 테스트가 된다. 대신 Vitest는
**브라우저 하네스가 비싸게 확인할 것들을 deterministic하게** 가져간다 — 셋 다 기존 레이어에 그대로 들어간다:

1. **threshold·집계 로직 → `e2e/perf/stats.mts`.** 샘플에서 p95를 내고 budget과 비교하는 부분은 순수 로직이다.
   앱 코드가 아니라서 `lib/`이 아니라 하네스 옆에 두고, Vitest 기본 glob이 `stats.test.mts`를 수집한다.
   `docs/testing.md`의 기존 규칙 "Every limit gets a test at exactly that value"가 문자 그대로
   적용된다 — 1000ms budget이면 999 / 1000 / 1001에 테스트를 둔다.
2. **round-trip 횟수·구조적 속성 → 클라이언트 컴포넌트 레이어.** 셋 중 값어치가 가장 크다. budget을 실제로
   깨뜨리는 건 "느린 코드"가 아니라 **round trip이 하나 늘어나는 변경**이기 때문이다. 참가 응답에 접속자
   목록이 이미 실려 오는데 별도 fetch를 한 번 더 하도록 바뀌면, 3초 budget이 2×RTT부터 시작한다.
   `fetch` 스파이로 "두 UI가 참가 응답 하나에서 렌더된다"를 assert하면 타이밍 없이 그 regression을 잡는다.
   클래스 B도 같은 모양 — WS 프레임에서 바로 렌더하는가, 아니면 refetch를 트리거하는가.
3. **instrumentation 훅의 계약 → `lib/`/`server/` 레이어.** 클래스 B의 ack·에코 instrumentation을 넣게 되면,
   플래그 없이는 꺼져 있는지와 프로덕션 설정에서 켜지지 않는지를 검사한다. v0.1.0 캠페인은 제품에 훅을 넣지
   않으므로 지금은 해당 없다.

알고리즘 regression을 막고 싶으면 ms가 아니라 **호출 횟수**를 assert한다(`vi.fn()` 스파이) — 머신 독립적이라
CI 게이트로 쓸 수 있다. `vitest bench`는 머신마다 숫자가 달라 게이트가 될 수 없으므로 도입하지 않는다.
